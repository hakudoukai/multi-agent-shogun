## §3 鳴らし方(loud)の設計

override 検知の主体は `scripts/lib/00e_gate_thresholds.sh`(追補2 §6-1・design のみ)自身とする
——**値を読む箇所と、override を検知する箇所を分けない**(追補1 §A-2「一箇所」原則を、閾値読込にも適用)。

```sh
# 疑似コード(design のみ・未実装)
_00e_load_threshold() {
  local var_name="$1" file_default="$2"
  local effective="${!var_name:-$file_default}"
  if [ "$effective" != "$file_default" ]; then
    _00e_announce_override "$var_name" "$file_default" "$effective"
  fi
  printf '%s' "$effective"
}
```

`_00e_announce_override()` が行う 3 手順(順序も設計の一部・§4 で理由を書く):

1. **ledger 追記を先に行う**(§4)。
2. ledger 追記が成功した後にのみ、`scripts/karo_second_send_iincho.sh --live --type status_update --requires-response`
   を呼ぶ(§5)。
3. 標準出力に `[ENV-OVERRIDE-USED] var=<VAR> file_default=<default> effective=<value> at=<ISO8601> ledger=OK|FAIL uplink=OK|FAIL`
   を itemize する(本体§5-3「うるさく失敗する」の型を踏襲・新形式の発明ではない)。

**gate 自体の exit code は override を理由には非 0 にせぬ**(override は裁定⑵により正当な出口ゆえ)。
但し **ledger 追記または uplink 呼出が失敗した場合は非 0 とする**
——「鳴らす機構が黙って失敗する」事こそが本裁定の禁ずる「半のまま」の再来であるゆえ(§9-②とも対応)。

## §4 消せない形(裁定一点目)

追補2 §4-1 の「`docs/00e_gate_release_ledger.md` は A種(git 追跡下)ディレクトリに置く」という決定を、
override 記録にも★流用する(新設の台帳を作らぬ)★。ただし REQUEST/APPROVED とは行の型を分ける
(解除申請と override 使用は別の出来事であり、同じ行型に混ぜれば追補2 §4-3 の読み手ロジックを壊す)。

### §4-1 新しい行型(OVERRIDE)

```
OVERRIDE var=<VAR> file_default=<default> effective=<value> by=<agent_id> at=<ISO8601> \
  status=半(fail-closed維持・出口温存) tier_chosen=③検知+④様式 tier_rejected=②機械ブロック \
  tier_reason="②は唯一の出口(override)を殺すゆえ裁定⑵に反する" ack=未実読確認
```

append-only(追補2 §4-2 と同一運用規約)。**「先に ledger へ書いてから override を効かせる」順序**(§3 手順1→3)
により、override 適用直後に process が異常終了しても、記録は既にディスクへ落ちておる
——「使われた事実」と「使われたと誰かが知った事実」を分け、前者を先に確定させる設計。

### §4-2 §5-4(本体)・§5③(追補2)自己適用検定の対象拡張

本体§5-4・追補2§5③は「門script自身」「閾値file」「解除台帳file」を対象とした。
本追補は同じ検定対象リストに**この ledger の OVERRIDE 行の書き込み関数自体**を加える必要はない
(書き込み先 file は追補2 §4-1 と同一 `docs/00e_gate_release_ledger.md` であり、検定対象は既に含まれておるゆえ
★新規追加は不要=既存の網に収まる事を確認したのみ★、と明記する)。

## §5 届け先 + 実読確認(裁定二点目・最も難しい所)

### §5-1 技術層(uplink)= 既存 helper の流用

`scripts/karo_second_send_iincho.sh --live --type status_update --requires-response -- "<OVERRIDE行と同内容>"`
を呼ぶ。この helper の POST が返す HTTP 200 / DB insert 成功は、**§2 で確認した通り machine ACK の一種に過ぎず、
委員長殿の実読の証にはならぬ**(裁定二点目そのもの)。

### §5-2 人間層(実読確認)= 新規の認証機構は作らぬ・既存の応答待ちパターンを流用

技術的に「読んだ事」を強制検出する新規機構(既読ピクセル・強制 ACK API 等)は、
DD-174 の申し送り憲法級 bible が既に禁ずる領域(Phase B 繰延・新規セキュリティ機構の作成禁、CLAUDE.md 該当節)に
触れかねぬゆえ、★本追補では作らぬ★。代わりに:

- ledger の `ack` field は既定 `未実読確認` のまま置く。
- 委員長殿(または裁定代理の副委員長殿)が override 事案に触れる**明示の返信便**(karo-second 経由でも直でも可)を発したら、
  その返信便の `at` を参照 payload とする第二行を追記する:

```
ACK_BY_APPROVER var=<VAR> ref=<OVERRIDE行のat> by=<approver_id> at=<ISO8601>
```

- **`ACK_BY_APPROVER` 行が無い限り、OVERRIDE 行の `ack` は `未実読確認` のまま表示され続ける**
  (追補2 §4-3「REQUEST のみでは解除にならぬ」と同型 — ★申請/通知だけでは確認にならぬ★という一貫した設計原則)。
- 未確認のまま時間が経った場合の催促は、既存の「30分以上応答が無ければ催促する権利がある」運用慣習
  (当職自身の task 完了定義に既に明記されておる下命)を override 確認にも適用する ——**新しいエスカレーション機構は作らぬ**。

### §5-3 「なぜ新規認証機構を作らぬか」の自己弁明

裁定二点目を字義通り満たすには「委員長殿が実際に読んだ」事を技術的に証明する何らかの機構が理想だが、
それは既読ピクセル等 Phase B 領域(DD-174・Security Phase 凍結、CLAUDE.md 該当節)に触れる可能性が高く、
★当職の裁量では作れぬ★。∴ 本追補は「技術層(uplink・machine ACK)」と「人間層(明示返信 = ACK_BY_APPROVER行)」を
分離した上で、後者が無い限り台帳上「未確認」のままにする事で、★確認できておらぬ事実そのものを隠さぬ★設計とした
——**証明できぬ物を証明したふりをしないのが、本裁定への最も誠実な応答**と当職は判断した(§8 新様式でも同じ点を明記する)。

## §6 台帳の書き方「半」固定語彙(裁定三点目)

- `status` field の許容値は★リテラル文字列 `半(fail-closed維持・出口温存)` の一種のみ★とする。
  `門`・`gate`・`ブロック`・`遮断` 等、完全封鎖を含意する語彙は禁ずる。
- 実装段階の負テスト(§10 ④相当)で、この語彙固定を機械的に検定できる形にしておく
  (`grep -c "status=半"` と `grep -c "OVERRIDE "` の行数が一致するか、という単純な突合で足りる——新規の複雑な検定機構は要らぬ)。
- ★「半」と書く事自体が目的ではない★。§1 裁定要旨の通り「実装されておるかを誰も測っておらぬ」事が委員長殿の元々の懸念であったゆえ、
  `status=半` の直後に **何が半で、何が全でないか**(= override は技術的に誰でも動かせる、実読確認は技術的に強制できぬ)を
  同じ行内に含める(`tier_reason` field がその役を兼ねる、§7)。

## §7 階層を下げた理由の明記(裁定三点目の続き・機構の順位)

機構の順位(karo-second 便より逐語): **①構造的不能化 > ②機械ブロック > ③検知 > ④様式**。

| 段階 | 本件での可否 | 採否 |
|---|---|---|
| ①構造的不能化 | env var 自体を読めなくする(例: systemd unit で `Environment=` を空に固定強制)。技術的には可能だが、**使い捨てrepo・自動テストでの正当な override 利用(追補2 §6-3 で許容した用途)まで一律に殺す**——過剰。 | 不採用(過剰) |
| ②機械ブロック | override 値を検出したら gate 自体を非 0 で止める。 | ★不採用★=**裁定⑵「override は唯一の出口であり、塞げば緊急時に詰む」に正面から反する**ゆえ、当職の裁量以前に裁定が既に退けておる |
| ③検知 | override 使用を検知し記録・通知する(§3〜§5)。 | **採用** |
| ④様式 | 台帳の書き方(status=半 固定語彙・tier_reason 明記・新様式「満たし得ぬ点」節)。 | **採用**(③と併用) |

∴ **本件は②が唯一の出口を殺すゆえ、③+④を選んだ**(karo-second 便「一 裁定 全文」の末尾指示への逐語対応)。
この一文自体を §4-1 の ledger 行型 `tier_reason` field へそのまま転記する設計とした(台帳が己の判断根拠を自ら持つ、追補2 §7 の「一箇所化」原則と同型)。

## §8 新様式 — 実装者が先に「満たし得ぬ点」を述べる(裁定五点目)

★本節自体が、この新様式を当職の報告(本追補)に適用した第一号である★。

**この設計が、受けた裁定を満たし得ない点**:

1. **裁定二点目(実読で確認・machine ACK を証拠にせぬ)を、技術的に完全には満たせぬ**。
   §5-3 で述べた通り、「実際に読んだ」事の技術的証明は Phase B 領域に触れかねぬゆえ作らず、

   台帳は永遠に `未実読確認` のままとなり得る(これは意図した挙動だが、「確認された」に転じる保証はどこにも無い)。

## §9 条⑿自己適用 — 己ならこの「鳴らす機構」をどう黙らせるか(最低3点)

**① 正規の入口(`_00e_load_threshold`)を経ずに env var を直接読む別実装を書く**
→ 追補1 §A-2「一箇所」原則により正規の入口は1つのみだが、shell の env var は OS 層で誰でも参照可能なため、
別 script が `${MY_VAR:-default}` を独自に読めば `_00e_announce_override` を一切経由せず override が効いてしまう。
→ 緩和: 完全には防げぬ(§8-2 で自己申告済)。既存の commit gate(軍師second PASS 必須)への依存として明記するに留める
(追補2 §5①と同型の限界)。

**② `scripts/karo_second_send_iincho.sh` への到達を断つ、または `--live` を付けず dry-run のまま紛れ込ませる**
→ 緩和: §3 手順の順序(ledger 追記を先に行い、uplink 呼出はその後)により、uplink が失敗・欠落しても ledger には残る。
但し★委員長殿への到達自体は防がれ得る★事は隠さず明記する。ledger 追記の失敗も uplink 呼出の失敗も、
gate の exit code を非 0 にする設計(§3)により**沈黙のまま成功したふりはできぬ**ようにしたが、
「非 0 で終わった事に誰も気付かぬ」可能性(既存監視インフラへの依存)までは本追補の範囲外。

**③ ledger 追記関数を改変し、`status` field を「半」以外の語(空文字・"OK"等)へ書き換えるコードを混入する**
→ 緩和: §6 で述べた通り、`status=半` の行数と `OVERRIDE ` 行の総数を突合する単純な負テストを設計に含めた(実装段階で実行)。
ただしこれも「負テストを実際に回す運用が続く」事に依存しており、負テスト自体を削除・無効化されれば見抜けぬ
(既存 Third-Party Audit 正本への依存、追補2 §5②と同型の限界)。
