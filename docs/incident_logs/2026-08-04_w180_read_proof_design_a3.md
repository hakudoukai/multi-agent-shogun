## §1 設計要旨 — 3点を実施可能な形に

W172で示した3点をそれぞれ機構に落とす:

| W172の3点 | 本設計での実装形 |
|---|---|
| ①台帳中身由来の具体事実の引用 | 「割当行番号」方式——path/要旨ではなく特定行の逐語引用を要求 |
| ②受け手grepの機械照合 | `sed`で正解行を取得→`grep -F`で報告文との部分一致を機械判定 |
| ③使い回し防止のローテーション | 割当行番号をtask_id由来のhashで決定+「既出台帳」で同一(agent,file,line)の再割当を禁止 |

## §2 手順 — 誰が・いつ・何を打てば判るか (実行可能形)

### Step A (発令時・karo-second側)

1. 対象file毎に候補事実行を機械抽出する(番号項目・表の行・強調段落の行番号一覧):
   ```
   grep -nE '^\*\*[^*]|^[0-9]+\.|^\|.*\|' <file>
   ```
2. 割当行番号を決める: `idx = sha256(task_id)の先頭8桁を16進→10進変換 % 候補行数`。
   task_idは発令時に既に確定しているため事前に一意に定まるが、
   ★karo-second・受信者いずれも算出前には値を知らぬ★(擬似ランダム性)。
3. 直近の「既出台帳」(下記Step D参照)を引き、同一(agent, file, 行番号)が既出なら
   idxを+1して次の候補行へずらす(単純な重複回避)。
4. task YAMLのcompact_recovery_read.filesへ`cite_line: <N>`を追記する(★本文は書かぬ——
   書けば写せてしまう。行番号のみ★)。

### Step B (実行時・受信足軽側)

5. 指定fileを実際に開き、`cite_line`の行を読む。
6. 最初の報告(work_started/ETA便)の冒頭に「参照した正本の具体事実」欄を設け、
   該当行の文言を逐語(または★を除去した形)で引用する。path/要旨のみの引用は不可。

### Step C (照合・karo-second側、機械grep — 明日そのまま打てる形)

7. 正解行を取得: `sed -n '<N>p' <file>`
8. 報告文と部分一致するか機械判定:
   ```
   sed -n '<N>p' <file> | grep -F -- "<報告文中の引用箇所>" && echo ACCEPT || echo REJECT
   ```
9. ACCEPT/REJECTを「既出台帳」へ追記(下記Step D)。

### Step D (既出台帳・永続化)

10. `docs/incident_logs/`配下に`w180_cite_ledger.md`のような追記専用(append-only)台帳を持ち、
    `(agent, file, line, task_id, 判定, 時刻)`を1行ずつ記録する。
    ★この台帳自体も「書かれるが読み返されぬ」七件目になり得る★(§7で後述)。

## §7 この工区が新たに開ける穴

1. ★最大の穴(§4と同一)★= grep一発で割当行だけを抜き出す「行番号カンニング」。
   引用文の機械照合は「その一行を入手した証」にしかならず、「意図された読解」の証にはならぬ。
   ★次にこの案を崩す者は、まずこの経路を試すべきである★(W172で当職が将軍案を崩したのと同じ構図)。
2. Step D「既出台帳」自体が★新たな「書かれるが読み返されぬ」資産候補★になり得る——
   karo-second・validatorがこれを実際に引いて重複判定に使わねば、
   ローテーション防止(③)は形骸化する。台帳を作ること自体は防御にならぬ。
3. 割当行番号の算出(`sha256(task_id) % 候補行数`)を担う実行者(karo-second本人 or 将来の
   validator script)に誤りがあれば、静かに同じ行が連続で割り当てられ得る——
   検証にはStep D台帳との突合が要るが、その突合自体を機構化していない(手作業依存)。
4. 「候補行」抽出パターン(§6)がfileごとに手作業で調整を要する場合、
   file構造が変わるたびに候補プールを作り直す運用負担が生じる——
   この運用負担が「面倒になって省略される」経路(本日何度も見た型)を新たに開く。
