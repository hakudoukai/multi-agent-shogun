## §A-1 要求の正確な中身

「稼働中の定義を書け」(本体§4)だけでは足りぬ。**定義を書いた後、それを呼ぶ場所を1箇所に絞れ**——これが今回の追加要求である。

委員長殿の実測が示した失敗形: 「ignored かつ active か」を問う主体が2つ(門・監視)あり、各々が独立に述語を実装した結果、**同じ file 群に対して 3件/5件 という異なる数が出た**。数の食い違いは「どちらかの実装のバグ」としてではなく、**述語が複数箇所に存在する事それ自体が原因**であり、個々の実装は各々正しく動いていても起こり得る(型②「両方在るが繋がっておらぬ」の亜種——今回は「繋がっておらぬ」のではなく「二重に存在し、繋がる先が2つある」)。

## §A-2 設計への反映 — 述語の単一化

本体§5-3で示した判定ロジック(信号A/B/C/Dの組合せ→ACTIVE/STALE/なし)を、**独立した1つの純関数として切り出す**:

```
判定対象の唯一の入口:
  is_ignored_and_active(repo_root, path) -> {status: FLAG|STALE|CLEAN, evidence: [...]}

呼び出し側(複数あってよい。実装が複数あってはならぬ):
  ① 巡回 script (本体§5-1) は is_ignored_and_active() を source して呼ぶのみ。
  ② 将来の pre-commit hook(§5-1 で「将来案」とした物)も同じ関数を source して呼ぶ。
  ③ 他隊(環境部長の未読警報 等、本件と主題が違う監視)が「ignored かつ active」を
     問う必要が生じた場合も、★独自に再実装せず本関数を呼ぶ★。
```

**配置場所**: `scripts/lib/ignored_active_predicate.sh`(既存 `scripts/lib/detect_stale.sh` と同じ置き場=`scripts/lib/` は既に「述語・判定ロジックの共通置き場」として使われておる前例があり、新形式の発明ではない)。

```
$ ls scripts/lib/
detect_stale.sh
```

→ 既存に倣い `scripts/lib/` へ追加する事を設計とする(実装(commit)は本追補の範囲外)。

## §A-3 「一箇所」を破らせぬ為の自己適用(§9 条⑿への追加点)

述語を1箇所に置いても、**呼ぶ側が「面倒だから」と inline で書き直せば同じ病が再発する**(委員長殿実測の直接の再現条件)。これを防ぐ具体策:

1. **命名を強く縛る**: 関数名 `is_ignored_and_active` を grep 可能な固有名にし、巡回 script・将来の hook いずれも冒頭で `source scripts/lib/ignored_active_predicate.sh` する事を「軍師second 監査のチェック項目」として明記する(監査時に `grep -L "source.*ignored_active_predicate" <呼出候補>` を打てば、再実装の有無を機械的に洗える)。
2. **本追補自身が「一箇所」の主張の実証**: 本体(§4・§5)は述語の中身(何が active か)を定義し、本追補(§A)は「その定義を置く場所」を定める。**両者を1つの file に混ぜず分けた**のは、まさに「同じ問い(稼働中とは何か / それをどこに書くか)を1箇所ずつでしか答えぬ」という本追補の主張を、本書自身の構成でも実践する為である。
