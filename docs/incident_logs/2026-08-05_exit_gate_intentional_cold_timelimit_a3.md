## §2 設計改訂 — expected_by を第三の必須欄とする

追補3 §2-2 の signal_type=`lane_intentional_cold` レコードへ、次を追加する。

```
signal_type: "lane_intentional_cold"
reason: <自由文・必須>
reopen_condition: <自由文・必須>
expected_by: <ISO8601・本追補で新規必須化>
recorded_at: <ISO8601>
```

**要点**: `expected_by` の中身 (条件が本当にそこで動くか) は判定せぬ — これは追補3の
用心⑴と同じ限界 (自己申告は配送の証に非ず)。★しかし「今の時刻が expected_by を
超えたか」は純粋な時刻比較であり、条件文の意味理解を要さぬ★。ここが本追補の核心 —
「意味を読む」問題を「時刻を比べる」問題へ縮小することで、自由文条件でも
時限判定だけは機械化できる。

### 2-1 状態遷移 (三値→四値への拡張)

| 条件 | 状態 | 報せ |
|---|---|---|
| reason/reopen_condition いずれか欠 | (intentional-coldでない・本体§4-2続行) | 通常のstale-alert判定 |
| reason/reopen_condition両方あり・now < expected_by | `suppressed-cold-open` | ★白★ (無音) |
| reason/reopen_condition両方あり・now ≥ expected_by | `suppressed-cold-aged` | ★灰→黒★ (弱い報せ) |
| reason/reopen_condition両方あり・expected_by欠 | (フォールバック適用・下記2-2) | expected_by代替値で上記いずれかへ |

### 2-2 expected_by 欠如時のフォールバック (「一週間鳴らぬ」を塞ぐ)

`expected_by` が書かれておらぬ既存記録 (00Dが現にこれ) に対し、★無期限の白★を
与えてはならぬ (これが将軍second殿の指摘そのもの)。∴:

**フォールバック値 = 該当事案の起票日時 (recorded_at) + 本体§4-1既定TTL (30分)**

すなわち `expected_by` を書かなんだ場合、本体が最初から持っていたTTL (30分) が
そのまま安全網として効く。「時限を書けば守られる強い意図」と「時限を書かねば
30分で灰へ落ちる」の二層になり、★意図の申告に時限を書かせる動機付け★も兼ねる。

### 2-3 弱い報せと強い報せの分離 (本体§4-4「共通出口state」への拡張)

- **強い報せ** (`stale-no-reason`) = reason/reopen_condition が欠けたままage>TTL — 従来のstale-alert。
- **弱い報せ** (`weak-aged-intentional`) = `suppressed-cold-aged` — 意図は示されたが期限切れ。

両者を同じ深刻度で扱わぬ (Commanderの誤検知を再生産せぬ・追補3§3-3の
`suppressed-cold-flagged`をここで具体化=`weak-aged-intentional`と同義に統合する)。
