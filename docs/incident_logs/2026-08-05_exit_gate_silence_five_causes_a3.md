## §3 設計反映 — 追補5§3-3の置き換え

### 3-1 門が自ら判じ得るのは⒞のみ (ただし二値化しない)

追補5§3-3は「⒝のみを機構が拾うべき」としたが、正しくは以下のとおり訂正する:

- **⒞のみ、門は機械的に検知できる** (context gaugeが数値で取得可能なため)。
  ただし§2-1のとおり、⒞検知は★単独ではstale-alertへ直結させない★ —
  「⒞かつ実際に応答が途絶えている (最終応答からの経過時間もTTL超過)」の
  ★複合条件★で初めて通知対象とする。これにより「飽和だが生きている」ケース
  (ashigaru6の実例) を誤検知しない。
- **⒜⒝は本人か外の目を要する** — 門はこれらを直接検知できない。追補5§3-3で述べた
  「⒝はreason/reopen_condition欄が構造的に埋まらぬためstale-alertへ素通しで拾える」
  という記述は★訂正しない★ (これ自体は妥当) が、「素通しで拾える」は「⒝であると
  識別して拾う」ことを意味せず、★単に無印stale-alertとして扱われるに過ぎぬ★ことを
  明確化する。門はこの便が⒜由来か⒝由来かを判別できない。
- **⒟⒠は実査を要する** — 門は「実際に手が空いているか」「見た目は沈黙だが中身は
  何か」を判定する手段を持たぬ。

### 3-2 「一語の下に五つ」への対応 — 出力の文言を分ける

追補4§2-3で当職は「強い報せ/弱い報せ」の二分を設計した。本書はこれをさらに一段、
★門が判じ得た範囲★と★判じ得なかった範囲★を出力文言で分けるよう改める:

```
[門が機械的に確認した範囲]
  - context使用率: N% (⒞判定に使用)
  - 最終応答からの経過: M分
[門が判じ得ぬ範囲・実査を要す]
  - ⒜(自己申告待ち) / ⒝(dialog等で申告不能) / ⒟(手が空いている可能性) の
    いずれかである可能性がある。門はこれらを区別できない。
```

★これが「門が為し得ぬ事を門にさせぬ」の本追補での具体化★ (karo-second便もこの当職の
既存作法を引用し「精一杯やも」と評した箇所)。「沈黙」という一語の出力を、
「門が確認した数値」と「門が確認し得ぬ可能性の列挙」の二段へ分けることで、
★読む者が『検知した』のか『検知できず実査を促しているだけ』かを区別できる★ようにする
(本体§4-2で確立した「判定不能は二値へ倒すな」の作法を、沈黙の内訳にも適用したもの)。
