## 案(a) auto_recovery 便の `type` を `task_assigned` 以外へ変へる

内容: `enqueue_recovery_task_assigned` が書く便の `type:` を、例へば `type: "auto_recovery_notice"`
の様な専用値に変へ、`has_task_assigned` の判定(=`type=="task_assigned"`を数へる)から除外する。

- **救ふ物**: `send_context_reset` の発火条件 `has_task_assigned` が此の便では立たなくなる ∴
  自己言及的発火の環そのものが断たれる。Phase3 エスカレーションの `/clear` 経路も同様に
  `type` を条件に使つてゐれば連動して塞がる(四版とも `has_task_assigned` の算出式を
  実測した上で確認要・本節は提案段階ゆゑ未確認)。
- **救はぬ物**: 便自体は届き続ける(`from=inbox_watcher`のnudgeは生きる)ので、
  「agentが/clear後に再着手を知る」機能は保たれるが、★他の`type=="task_assigned"`を
  前提に動く別ロジック(例: dashboard集計・監査対象抽出)が此の便を拾へなくなる副作用の
  有無は未検証★ ―― 全呼出箇所の横断調査が此の案の実装前提として別途要る。
- **変更統制**: 該当(封筒規約=`type`の意味の変更)。★委員長許可必須★。

## 案(b) auto_recovery はログにのみ書き、inbox には書かない

内容: `enqueue_recovery_task_assigned` を「inbox書込」から「ログ出力のみ
(`[CONTEXT-RESET]`と同様の `>&2` 出力)」へ変へる。

- **救ふ物**: inbox に未読メッセージが残らなくなる為、`has_task_assigned` は常に偽になり、
  自己言及的発火の環は原理的に成立しなくなる(最も確実に環を断つ)。
- **救はぬ物**: agent が `/clear` 後に「何をすべきか」を inbox 経由で再認識する経路が消える。
  現状 a1 の実例(`read: true`)が示す様に、★此の便こそが agent の再着手の根拠★になつてゐる
  ケースが在る ―― ログのみでは agent 自身がログを読みに行かぬ限り再着手の契機を失ふ。
  ∴ 「環は断てるが、再着手の自然な誘導も同時に失ふ」トレードオフ。
- **変更統制**: 該当(通知の配送経路そのものの変更)。★委員長許可必須★。

## 案(c) `from: inbox_watcher` の便は `/clear` の引金から除外する

内容: `has_task_assigned` (または `send_context_reset` の発火条件)の判定時、
`from` フィールドが `inbox_watcher` 自身であるメッセージを対象外にする
(=他者(家老等)が書いた真の `task_assigned` のみを引金として残す)。

- **救ふ物**: watcher 自身が書いた便が watcher 自身の次の発火根拠に成る自己言及的発火のみを
  狙ひ撃ちで断つ。家老等の人間相当役が明示的に送る本来の `task_assigned`(タスク新規割当)の
  `/clear` 誘発力は保たれる ―― 案(a)(b)より影響範囲が狭く、副作用が少ない見込み。
- **救はぬ物**: 判定条件に `from` の比較が増える分、実装・保守コストが上がる。また
  ★`from` 欄が省略/誤記された便★(過去便で稀に発生し得るか未検証)があれば
  誤つて対象外/対象内に分類される脆さが残る ―― 此の案は「envelope の`from`欄が
  常に正しく書かれてゐる」前提に依存する。
- **変更統制**: 該当(発火条件ロジックの変更)。★委員長許可必須★。
